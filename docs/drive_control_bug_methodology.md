# 电机控制 bug 处理方法论与安全原则

## 1. 结论先行

这次倒车/制动异常的核心不是“两个轮子硬件不同步”，而是控制逻辑把“倒车请求”与“制动/油门命令”混在同一条输出路径里，导致在状态切换、速度估计不稳或输入抖动时，系统把反向驱动命令送进了饱和区，表现为两个轮子出现前后乱窜、甚至接近最高速度输出。

## 2. 现象背后的根因

1. 方向命令和扭矩命令被混用。
   - 倒车请求本质上是一个“方向状态请求”，但代码中被直接映射为负方向驱动命令。
   - 当这个请求被错误触发或状态没有被正确清零时，就变成了实际输出。

2. 没有把“允许进入倒车”和“实际执行反向驱动”分成两个阶段。
   - 只要倒车请求成立，就可能把输出命令打成负方向。
   - 这在低速区、抖动、速度估计异常时尤为危险。

3. 反向输出缺少强约束。
   - 之前的逻辑没有把“车速方向、速度绝对值、刹车状态、油门输入”作为必须同时满足的条件。
   - 结果是异常情况下仍然会发出较大的反向命令。

4. 车轮控制器与混控器的延迟和不对称会放大这个问题。
   - 单侧的方向命令变化，被 FOC 控制器映射成左右轮的独立输出。
   - 这就会表现为看起来像“前后乱窜”。

## 3. 安全修复原则

### 3.1 先保证“安全边界”

任何反向驱动都必须满足以下条件：
- 车速绝对值必须足够低；
- 车体不能已经处于显著的正向运动；
- 不允许同时存在有效刹车输入；
- 反向输出必须被统一限幅。

### 3.2 把状态判断和执行输出分开

不要把“是否允许倒车”与“生成反向扭矩”混在一个变量里。应该分成两层：
- 请求层：判断是否允许进入倒车；
- 执行层：根据请求和安全条件生成实际输出。

### 3.3 所有方向相关输出必须可观测

至少要能看到：
- 输入油门；
- 制动踏板；
- 车速；
- 运动方向；
- 倒车请求；
- 最终输出命令。

## 4. 处理 bug 的方法论

### 4.1 先定位“问题发生在哪一层”

遇到这类问题时，先判断是以下哪一层出错：
- 传感器/输入层；
- 状态估计层；
- 状态机层；
- 输出/限幅层。

### 4.2 只修复根因，不做堆补丁

不要反复在同一段逻辑上加一刀一刀的临时判断。应该把根因抽象为“状态门槛不足”或“输出未受限”。

### 4.3 每次改动都回答三个问题

1. 这个改动会不会扩大范围？
2. 异常状态下是否仍然会发出驱动？
3. 是否只是把问题从一个症状挪到了另一个症状？

### 4.4 对人命相关系统，必须先安全再功能

电机控制不是普通的软件逻辑。只要出现方向、速度、制动相关问题，就必须先确保：
- 不会突然反向加速；
- 不会在低速时出现异常漂移；
- 不会因为一个输入抖动把控制输出打满。

## 5. 工程实践建议

- 对所有方向相关控制命令，必须有显式的安全阈值；
- 对倒车/制动逻辑，建议加一个清晰的“状态机”说明；
- 每次提交前，必须能从日志中判断当前是否进入了倒车、是否被安全限制；
- 任何涉及人身安全的控制代码，都应优先做静态逻辑审查和回归测试，而不是只靠现场试验。
