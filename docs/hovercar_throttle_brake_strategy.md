# Hovercar 油门 / 刹车 / 倒车策略说明

## 1. 目标

本策略的目标是：
- 油门释放时不要直接把输出打到 0，避免“突然失力”导致的抖动；
- 刹车要像真实物理制动一样，踩得更深时产生更强的反向扭矩；
- 倒车只在满足条件时才进入，且速度受限，避免危险的反向加速。

## 2. 输入与状态

当前控制逻辑在悬浮车模式下会同时关注以下状态：
- 油门输入：前进/加速命令；
- 刹车踏板输入：用于生成制动目标；
- 当前车速：用于判断正向、反向和低速区；
- 双击检测状态：用于在低速时允许短暂的倒车触发。

## 3. 油门策略

- 正常前进时，油门命令由当前输入和限速器共同决定；
- 释放油门时使用较慢的下降速率，避免“拔掉油门后立刻回零”；
- 低速时，命令会先通过滤波器和速率限制器，避免突变。

## 4. 刹车策略

- 刹车踏板被读取后，先转换成一个“制动目标”，而不是直接把命令硬改成反向输出；
- 制动目标会按踏板力度和当前车速进行缩放；
- 低速区和高速区使用不同的增益，保证低速起步时制动更平顺；
- 制动目标会经过一个缓慢上升/下降的斜坡，避免瞬间翻转。

### 4.1 关键参数

- BRAKE_PEDAL_THRESHOLD：刹车踏板触发阈值；
- BRAKE_MIN_SPEED_RPM：低速时制动增益开始生效的最低速度；
- BRAKE_SMOOTH_ZONE_RPM：制动增益从 0 线性过渡到满量程的区间；
- BRAKE_RAMP_STEP：制动目标的斜坡步长；
- BRAKE_MAX_LIMIT：制动目标的最大幅值。

## 5. 倒车策略

- 只有在低速区且检测到双击刹车时，才允许进入“倒车请求”；
- 倒车请求只有在存在实际油门输入时才会生成反向驱动；无输入时会快速回零，不会持续后退；
- 倒车时依然经过同样的滤波和限幅流程，避免出现突兀的方向反转。

## 6. 左右轮方向说明

左右轮方向之所以要相反，是因为车轮需要通过“相反的转向”来产生前进或后退的推进力。

在当前混控逻辑里：
- 右轮命令和左轮命令由同一个速度命令与转向命令混合得到；
- 正常直线前进时，左右轮需要以相反的电机极性输出，才能让车体整体朝同一个方向移动；
- 方向反转时，控制逻辑会根据实际电机方向和方向反转宏定义，保证速度正负号和车轮实际转向一致。

## 7. 串口调试输出

串口输出中新增了以下字段，便于实时观察策略状态：
- rev：是否触发了倒车请求；
- tap：双击检测是否成立；
- dir：当前运动方向；
- br：当前踏板输入幅值；
- bt：当前制动目标；
- fbc：滤波后制动命令；
- thr：当前实际用于限速器的油门/制动目标。

通过这些字段，可以快速判断当前是不是进入了倒车、是否产生了制动、以及制动目标是否被正确限制。

## 8. 最近修复与讨论要点

### 8.1 本次问题的根因

这次出现的现象并不是单纯的“两个轮不同步”，而是控制链路把“倒车请求”与“制动/油门命令”混在同一条输出路径中，导致以下几类问题同时出现：

1. 倒车请求一旦触发，就把输出命令直接变成负方向驱动；如果输入抖动、速度估计不稳或者状态切换时序不一致，就会把命令送到饱和区。
2. 之前的逻辑把制动、倒车和油门都写成同一个 `throttleCommand`，缺少一个“状态机级”的安全门槛，导致正向速度或速度估计异常时仍然存在反向驱动力。
3. 车轮实际响应存在延迟与不对称，且 FOC 控制器本身会把输入命令映射成相对独立的左右轮输出，因此看起来像“前后乱窜”，实际上是一个方向命令和限幅条件失控的结果。

### 8.2 这次修复的基本原则

本次修复没有再继续堆砌“补丁式”的特判，而是遵循以下方法论：

- 优先保证“安全边界”而不是“功能看起来能动”；任何反向驱动都需要满足低速、低速误差和无刹车条件。
- 把“状态判断”和“命令生成”分开：状态先判断是否允许进入倒车，再生成对应的反向输出；不要在状态判断失败时仍然把命令送进限速器。
- 所有反向输出都要经过统一的幅值限制，避免因为输入抖动或控制器内部状态变化而飙到极限值。
- 任何新的控制逻辑都要有可观测的字段，便于在日志中判断到底是“没有进入倒车”、还是“进入倒车但被限制了”。

### 8.3 经验总结：如何避免这类事故级 bug

电机控制是人命关天的系统，不能用“看起来能跑”来代替“严谨验证”。建议遵循以下方法论：

1. 先从状态机画出所有可能状态：空闲、前进、制动、倒车、锁定、异常；每个状态的进出条件必须明确。
2. 把控制输出分成“请求”和“执行”两层：请求层决定是否允许切换，执行层再根据安全条件生成实际扭矩。不要混在一个变量里。
3. 对任何会影响方向的变量，必须同时观察：输入、速度、方向、刹车状态、限速器输出。
4. 每次改动都要能回答三个问题：
   - 这个改动会不会扩大范围？
   - 这个改动是否会在异常状态下仍然发出驱动？
   - 这个改动有没有把问题从一个症状移到了另一个症状？
5. 代码提交前必须让日志字段足够清楚，至少包含：输入、车速、方向、制动目标、反向请求、最终输出命令。

### 8.4 处理意见

如果出现类似问题，首先不要继续“盲修”。应当先回到以下顺序：

- 先确认日志中哪些字段已经进入了错误状态；
- 确认是“状态判断错了”还是“命令生成错了”；
- 只修复根因，不再堆砌临时补丁；
- 对安全相关逻辑加上强约束，避免任何单点异常把输出拉满。


- 修复了“倒车油门同时踩刹车时丢失制动力”的问题：当刹车被按下且处于倒车请求时，会优先保留刹车制动力而取消倒车输出，保持阻力感觉。
- 进一步避免了“零速硬切换”的刀锋效应：零速附近不再直接使用带方向的全额反向力矩，而是在速度极低时使用小幅静态阻尼。
- 当前的刹车和倒车逻辑仍然经过滤波与斜坡控制，确保制动力和倒车力不会直接以阶跃信号送到电调驱动器。
- 如果要调整制动效果，推荐修改 `Inc/config.h` 中的以下宏：
  - `BRAKE_MAX_LIMIT`：刹车目标最大幅值；增大可提高最大制动力。
  - `BRAKE_RAMP_STEP`：制动目标斜坡步长；减小可使制动更平顺，但响应更慢。
  - `BRAKE_PEDAL_THRESHOLD`：刹车触发阈值；增大可让刹车输入更迟钝。
  - `BRAKE_MIN_SPEED_RPM` / `BRAKE_SMOOTH_ZONE_RPM`：低速时制动增益过渡区；调整可改变低速刹车的柔顺度。
  - `REVERSE_SPEED_LIMIT`：倒车油门最大值；只影响倒车时的最大反向驱动量。
